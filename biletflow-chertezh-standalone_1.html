01

С чего начать

Не с экранов и не с логина. Первое, что нужно зафиксировать, — модель данных и контракт API. Пятеро не смогут работать параллельно, пока не договорятся, как выглядит заказ и что возвращает чекаут.

SRS описывает 25 сущностей и четыре роли. Если начать с кода экранов, к пятой неделе окажется, что у веба одна форма заказа, у мобилки другая, а бэкенд не умеет ни ту, ни другую. Порядок первых двух недель:

Сначала — только ядро

Полная схема — 34 таблицы, полное API — 92 метода. Строить это разом нельзя. Разделите на две фазы: сначала то, без чего сценарий не проходит, потом всё остальное — по одной функции.

Фаза 1 — ядро (11 таблиц, ~20 методов)Фаза 2 — после того, как ядро работает
Аккаунты и профиль организатора Назначенные места и карта зала (5 таблиц)
Событие: создать, опубликовать, отменить Промокоды и Campaign QR (5 таблиц)
Типы билетов и остатки Чат поддержки (2 таблицы)

Мобильный чек-ин по QR Уведомления, аудит, аналитика, календарь

Ядро лежит в schema-core.sql — это одиннадцать таблиц: users, organizer_profiles, events, staff_assignments, ticket_types, orders, order_items, attendees, tickets, check_in_records, payments. Площадка в нём — просто две текстовые строки, активация платных продаж — один BOOLEAN, токены подтверждения почты — колонка в users. Всё, что можно было свернуть, свёрнуто.

Что при этом не упрощается

Четыре защиты остаются даже в ядре: нельзя продать больше, чем есть; бесплатный билет не может стоить денег; один билет пропускает ровно один раз; повторный вебхук не выпускает второй комплект билетов. Это не усложнение — это то, ради чего вообще нужна база вместо файла с JSON.

Неделя 1 — фундамент

  1. Репозиторий и Docker. Один monorepo, три пакета: api/, web/, mobile/. docker-compose up должен поднимать Postgres + API + веб одной командой с первого дня.
  2. Схема БД в Alembic. Берёте schema-core.sql, он и становится первой миграцией. Полный schema.sql держите рядом как картину, куда растёте.
  3. OpenAPI как договор на старте. openapi.yaml кладётся в репозиторий, фронт и мобилка генерируют из него типы и поднимают мок-сервер, не дожидаясь бэкенда. Как только появится код, источником правды станет он: FastAPI отдаёт спеку сам на /openapi.json, вручную вести yaml не надо — он протухнет за неделю.
  4. Аутентификация. Регистрация, подтверждение почты, JWT, зависимости FastAPI для проверки ролей. Это блокирует всех остальных, поэтому делается первым.

Неделя 2 — вертикальный срез

Одна тонкая, но сквозная функция целиком: организатор создаёт бесплатное событие → посетитель регистрируется → приходит письмо с QR → ивент-админ сканирует его в приложении и видит «Проход разрешён». Без оплат, без мест, без промокодов.

Зачем именно так

Этот срез задевает все пять частей системы: API, веб организатора, веб посетителя, почту и мобильное приложение. Как только он работает, дальше вы наращиваете функции на живом скелете, а не собираете пять кусков в конце семестра. Это же и есть основной сценарий демонстрации из §13.4 SRS.

Чего не делать в первые недели

Не браться за карту мест, промо-кампании и аналитику. По плану SRS это недели 7–9, и они честно помечены как то, что вырезается первым, если проект отстаёт. Карта мест — самая дорогая функция в проекте и единственная, где ошибка проектирования заметна пользователю сразу.

02

Архитектура

Один бэкенд, три клиента. Микросервисы прямо запрещены рамками курса (§9 SRS) и здесь не нужны: у платформы одна транзакционная база и один источник правды по инвентарю.

Почему модульный монолит, а не микросервисы

  • Инвентарь требует транзакций. «Проверить остаток → удержать место → применить промокод → создать заказ» должно быть одной ACID-транзакцией. Разнесите это по сервисам — и вам придётся писать сагу с компенсациями. За 12 недель это не делается.
  • Границы модулей всё равно нужны. Модули не лезут в чужие таблицы напрямую: только через сервисный слой соседа. Если после курса захотите вынести что-то в сервис — границы уже прочерчены.

Вся инфраструктура — три контейнера

Ни Redis, ни Celery, ни брокера, ни отдельного планировщика. Postgres хранит данные, MinIO хранит файлы, FastAPI делает всё остальное. Меньше контейнеров — меньше того, что сломается за час до защиты.

services: db postgres:16 # все данные storage minio/minio # PDF-билеты, афиши, картинки QR api ./api # FastAPI: роуты + фоновые задачи web ./web # React, только для разработки

MinIO — это S3 у вас на машине. Тот же протокол, что у Amazon S3, поэтому код пишется через boto3 и при желании переезжает на настоящий S3 сменой трёх переменных окружения. На защите же всё поднимается одной командой без интернета.

Фоновые задачи без очереди

HTTP-ответ на чекаут не должен ждать генерации PDF или отправки письма. Но очередь для этого не нужна — хватает того, что уже есть в FastAPI.

ЗадачаКак делается
Выпуск билетов после оплатыСинхронно, прямо в обработчике вебхука. Это несколько INSERT — они занимают миллисекунды. Очередь здесь только добавила бы способ потерять билеты
Письмо с билетом, рендер PDFBackgroundTasksFastAPI: ответ уходит сразу, задача выполняется после него в том же процессе

@asynccontextmanager async def lifespan(app: FastAPI): task = asyncio.create_task(sweep_expired()) # стартует вместе с приложением yield task.cancel() async def sweep_expired(): while True: async with session() as db: await db.execute(text(""" UPDATE seat_holds SET status = 'expired' WHERE status = 'active' AND expires_at < now() """)) await db.commit() await asyncio.sleep(60)
Единственный минус такого подхода

Если процесс перезапустится ровно между ответом и отправкой письма, письмо потеряется. Билеты при этом уже выпущены и лежат в базе — теряется только доставка. Закрывается кнопкой «выслать билеты повторно» (POST /orders/{id}/resend-tickets), которая всё равно нужна: письма теряются в спаме гораздо чаще, чем от перезапусков.

03

Модель данных

34 таблицы, из них ядро — четырнадцать. Полный DDL с индексами и ограничениями лежит в schema.sql; ниже — ядро, вокруг которого крутится всё остальное.

Четыре решения, которые стоит принять сейчас, а не переделывать в декабре

Деньги — целые числа в тиынах

Все суммы хранятся как BIGINT в тиынах: 15 000 ₸ — это 1500000. Никаких float и numeric для расчётов. 20% скидки от трёх билетов по 4 990 ₸ в плавающей точке даст итог, который не сойдётся с суммой строк заказа, и вы будете это ловить неделю.

Инварианты живут в базе, а не только в коде

Ключевые ограничения выражены как CHECK и частичные уникальные индексы. Даже если два запроса придут одновременно и код проверит остаток одинаково, вторая вставка упадёт на индексе.

Что защищаемМеханизм в PostgreSQL
Одно место — одно активное удержаниеUNIQUE (event_id, seat_id) WHERE status='active'
Одно место — один действующий билетUNIQUE (event_id, seat_id) WHERE status IN ('valid','checked_in')
Нельзя продать больше, чем естьCHECK (quantity_held + quantity_sold <= quantity_total)
Один билет — один проходUNIQUE (ticket_id) WHERE action='check_in'
Итог заказа сходится со строкамиCHECK (total = subtotal − discount + fee)
Лимит промокампании не превышаетсяCHECK (redemption_count <= max_redemptions)
Бесплатный тип билета не может стоить денегCHECK (kind='free' AND price=0 OR kind='paid' AND price>0)
Повторный вебхук не выпустит второй билетUNIQUE (provider, provider_event_id)

Снимок места в билете

В tickets рядом с seat_id лежат текстовые seat_section_name, seat_row_label, seat_label. Организатор может переименовать ряд после продаж — уже напечатанный билет от этого «поехать» не должен.

История — это append-only таблица

Лента активности события (§4.16) и аудит (§7) — одна таблица audit_log, куда приложение только вставляет. В продовой миграции у роли приложения отзываются UPDATE и DELETE на неё. Полной версионности полей MVP не требует.

04

Три опасных места

Остальное в проекте — обычный CRUD. Эти три потока — те, где наивная реализация проходит демонстрацию и ломается при двух одновременных пользователях.

А. Выбор места и чекаут

Классическая гонка: двое одновременно жмут на кресло 7 в первом ряду. Решение — сначала взять удержание в базе, и только потом показывать корзину.

Правило, которое нельзя нарушать

Скидку считает только сервер. POST /promo-codes/validate — это предпросмотр для интерфейса, он ничего не резервирует. Реальное применение промокода и списание лимита происходят внутри той же транзакции, что и создание заказа.

Б. Чек-ин по QR

В QR лежит не ticket.id, а непрозрачный ticket_code с HMAC-подписью. Подделать билет, зная схему нумерации, невозможно; сканер при этом не должен ничего решать сам.

  • Отказ — это тоже HTTP 200. Сканер всегда получает структурированный result, а не исключение. Ошибки 4xx остаются для настоящих ошибок вызова.
  • Кто отметил — видно. Каждая запись хранит performed_by, поэтому организатор видит, кто из сотрудников сколько гостей провёл. Это то, что и просили в заметках — и почти бесплатно, раз запись всё равно создаётся.
  • Отмена прохода не удаляет запись, а добавляет новую с action='reversal' и требует отдельного права can_reverse_checkin.

В. Campaign QR и промокод

Это второй тип QR в системе, и его легко перепутать с билетом — а он не даёт прохода. В SRS это отдельным пунктом (§4.14), и не зря.

Два QR — две вселенные

Билетный QR содержит ticket_code + HMAC. Campaign QR содержит campaign_token и ведёт на HTTPS-ссылку. Эндпоинт /checkin/scan обязан явно распознавать второй и возвращать campaign_qr_not_admission — иначе кто-нибудь пройдёт на концерт по рекламной листовке. Это отдельный обязательный тест.

05

Жизненные циклы

Три конечных автомата, которые стоит закодировать явно — переходы разрешены только по стрелкам, всё остальное отвергается на уровне сервиса.

Важно, что это две независимые оси. Событие может быть опубликовано и продавать бесплатные билеты, пока платные продажи ещё не активированы. Именно в этом смысл монетизации из §3 SRS: бесплатное всё, платить — только когда собираешься зарабатывать.

Билет проще: valid → checked_in при первом проходе, valid → cancelled | refunded при отмене или возврате. Обратного пути из refunded нет; ошибочный проход снимается записью reversal, которая возвращает билет в valid.

Сквозные соглашения

  • Идемпотентность. /checkout, /payment-intent и /checkin/scan требуют заголовок Idempotency-Key. Двойной клик и повтор вебхука не создают дубль.
  • Авторизация — по связи, а не по роли. «Организатор» ничего не значит без привязки к конкретному событию. Каждая проверка отвечает на вопрос «этот пользователь имеет отношение к этому событию?».
  • Ошибки — RFC 9457 (application/problem+json): FastAPI отдаёт это одним обработчиком исключений, фронт разбирает единообразно.
  • Пагинация — курсорная. На списках гостей и заказов offset начнёт врать, как только кто-то оформит заказ во время пролистывания.

Репозиторий

Один monorepo. Общие типы генерируются из openapi.yaml, поэтому переименование поля на бэкенде ломает сборку фронта — что и требуется.

Про ADR

Каждое архитектурное решение — одна страница: контекст, варианты, выбор, последствия. Это ровно то, чего требует §9 SRS («выбор стека документируется с кратким обоснованием»), и это же спасёт на защите, когда спросят «почему PostgreSQL, а не Mongo».

09

Решить на этой неделе

Из §12 SRS — открытые вопросы, которые блокируют разработку. Остальные могут подождать; эти нет.

  • Обязателен ли аккаунт посетителю? Схема допускает гостевой заказ (buyer_user_id может быть NULL, доступ по подписанной ссылке из письма). Это заметно повышает конверсию, но усложняет «мои заказы». Решение меняет чекаут и письма — решайте до недели 5.
  • Ивент-админ — обязательно пользователь платформы? Схема исходит из «да»: назначение по email, журнал прохода с именем сотрудника. Иначе не будет понятно, кто кого провёл — а вы сами хотели эту функцию.
  • Комиссию за обработку платит организатор или посетитель? Влияет на fee_minor в заказе и на то, что видит покупатель в итоговой сумме. Для MVP проще: комиссии нет, только разовый активационный сбор.
  • Размер активационного сбора и возвратность. Нужно любое конкретное число для демонстрации. Возьмите правдоподобное и запишите в ADR.
  • Какая площадка станет предзаготовленным layout'ом? Нужен ровно один зал с секциями, рядами, доступными местами и ценовыми категориями. Возьмите реальный зал вашего вуза — данные для сида готовятся заранее.
  • Песочница провайдера или собственная симуляция? От этого зависит неделя 5. Симуляция быстрее и полностью под контролем на защите; песочница честнее. В любом случае каждый экран с деньгами обязан быть явно помечен как демонстрационный.
